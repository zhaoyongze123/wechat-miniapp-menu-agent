# 微信小程序菜单导航 Agent PRD

**版本** v0.1 · 全自动批量试验  
**当前进度** 代码接入和本地联调已完成，支持全自动批量试验，真实微信评测在试验目录独立留存。

## 1. 背景与目标

采集人员打开门店小程序后，通常还要经过欢迎页、广告、人数选择或其他中间操作，才能进入菜单。同一类操作在不同小程序中的顺序、文案和布局都可能不同。现有流程依赖 OCR、场景规则和视觉模型协同处理，遇到规则未覆盖的页面时，需要重新分析和适配。

历史输出审计也发现，部分被记为采集成功的文件实际包含弹窗、订单页、错店菜单或截断内容。问题在 1–3 页和多页结果中都出现过，因此验收需要同时看门店身份、画面内容和采集完整性。 [2026-11-08 采集质量审计](../outputs/采集质量审计-20261108.md)

本次目标是让 **GUI Agent 从已打开的目标小程序自主进入可采集菜单**。Agent 根据当前画面决定下一步，观察动作结果，再调整操作或给出终态。采集人员可以回看结论、理由和画面证据。

## 2. 用户与首版范围

主要用户是负责门店菜单采集和复核的运营人员，以及负责排查动作失败的开发人员。

| 环节 | 首版范围 |
| --- | --- |
| 启动前 | 操作员选中一条已有门店任务，手动打开对应的微信小程序，让目标窗口保持前台。素材清洗、批次版本和二维码环节沿用现有流程。 |
| 菜单导航 | Agent 独立观察、点击、滚动和等待，处理到达菜单前的多步交互，并自行判断业务终态。 |
| 截图采集 | 导航成功后，现有采集器接收终态画面和菜单区域，执行滚动截图，结果暂存供核验。 |
| 试验与回退 | 通过本机全自动试验入口运行。旧流程独立可选。切换路径时由操作员结束本轮并重新启动，试验期间无自动回退。 |
| 评测范围 | 11 家真实门店由 UiPath 逐店打开小程序，再独立评估 Agent 的端到端导航。19 个固定画面和 R01 用于离线诊断。 |
| 批量接入 | 完成 11 家评测并独立复核运行证据后，再决定是否接入生产批量。 |

## 3. 用户流程

1. 按清单启动批量试验。UiPath 使用登记的二维码逐店打开小程序，并在切换门店前确认回到文件传输助手。
2. 系统记录目标门店和配置的用餐人数。Agent 获取目标窗口截图，根据目标自行决定每轮动作。每次执行后获取新画面，供 Agent 判断操作是否生效。
3. Agent 给出导航终态和理由。成功时附菜单滚动区域和画面证据，系统交给现有采集器。
4. 操作员查看本轮报告、终态截图和试验产物，独立核对门店及菜单。遇到窗口失焦、超时或无法继续，可终止试验并保留已有证据。

## 4. 导航结果

| 状态 | 判定口径 | 结果交接 |
| --- | --- | --- |
| `success` · 已进入菜单 | 可确认是目标门店，菜品与价格可读，菜单区域无遮挡且可用于滚动采集。打烊后仍可浏览菜单的门店可以成功。 | 保存理由、终态截图和菜单区域，进入试验采集。 |
| `unqualified` · 门店不合格 | 当前画面有证据证明目标门店本身不可采。例如门店明确停用扫码点餐、页面显示菜单未配置，或能确认是商家侧网络异常。 | 保存原因码、具体理由和对应截图。试验结论只写入本轮报告。 |
| `needs_review` · 需人工复核 | 门店身份无法确认、需要登录或授权、页面长期加载且原因不明，或执行超时、截图和坐标校验失败。 | 保留理由及已有画面。系统层中断另记 `source: runtime`，与 Agent 主动请求人工区分。 |

**导航终态与采集结果分别记录。** 导航 `success` 代表菜单已具备交接条件。试验截图标为 `staged` 时，仍需核验是否正确、完整。菜单只有一页也可以通过，前提是证据能支持内容完整。

## 5. 产品与技术要求

| 要求 | 首版行为 |
| --- | --- |
| 自主导航 | 字节 GUI Agent SDK 2.0（`@gui-agent/agent-sdk@0.3.1`）持有执行循环和上下文，百炼 `gui-plus-2026-02-26` 判断动作与终态。Python 管理任务、执行边界和交接。新路径独立于旧页面规则，避免重复维护导航决策。 |
| 只读执行 | 复用 UiPath 的窗口截图、单击、有限垂直滚动和等待。一轮只执行一个动作，坐标必须对应最新截图和当前窗口。任务指令禁止点菜、加购、下单、支付、领券、登录、切换门店或授予新权限。 |
| 结果可追溯 | 报告关联本轮任务、导航状态、原因、截图及采集页。保留窗口动作记录，便于区分识别错误、点击偏移、页面无响应和执行器异常。 |
| 成果隔离 | 试验写入独立目录，正式任务状态和不合格清单保持独立。正式产物按清洗批次 ID 和门店组织，同批次同店重新采集成功后替换已有结果。历史未核验结果单独归档。 |

GUI-Plus 的动作在回复正文中返回，适配器负责解析并交给 SDK。模型使用相对于当前送模图的 1000×1000 归一化坐标。程序按本轮截图尺寸转换到 UiPath 窗口坐标，真实桌面点击前用合成图验证落点。 [SDK 源码](https://github.com/bytedance/UI-TARS-desktop/blob/20b2dfe85e0a84eb2fe7b2f5db1c2807a4c8d829/multimodal/gui-agent/agent-sdk/src/GUIAgent.ts) · [百炼 GUI-Plus 指南](https://help.aliyun.com/zh/model-studio/gui-automation)

## 6. 验收与放量

### 6.1 执行验收

| 验收项 | 通过标准 | 当前状态 |
| --- | --- | --- |
| 本地协议与执行边界 | 模拟流式模型响应下，点击后新截图进入下一轮。三种终态可区分，旧格式和无效证据被拒绝，终止后停止派发动作，试验结果独立留存。 | 本地测试通过。 |
| 真实模型坐标 | 使用百炼北京地域凭据，让模型在非方形合成图上给出已知目标的点击坐标。换算后的点落在标记区域内。此阶段不连接真实鼠标。 | 待验收。 |
| 真实批量端到端 | 按清单自动打开门店并运行 Agent。核对每家终态、门店身份、首尾截图、连续性和可见分类。 | 以本轮证据为准。 |

### 6.2 核心实机评测口径

核心评测覆盖评测集 `live_cases` 的 11 家。按 `suggested_live_order` 将任务列表传给全自动入口，使用任务原本登记的素材快照。UiPath 自动完成扫码及开窗，Agent 从首帧开始自主导航。全程保持无人为干预，提示词对所有门店统一。

人工评审根据本轮首帧、动作回执、过程截图、终态、采集产物和报告，先独立裁定实际业务状态，再与 Agent 给出的终态比较。历史标签和用例描述仅用于准备，不代替对运行证据的判断。每轮分别记录：

- **自主导航**：是否实际进入可交接菜单，目标门店身份是否正确；订单页、遮挡页或错店不得算成功。
- **业务终态准确性**：Agent 的 `success`、`unqualified` 或 `needs_review` 是否与人工依据运行证据裁定的状态一致。
- **救援**：人工接管或重开次数、时间点、原因及前后结果。救援后的成功不能计为自主成功。
- **历史失败挽回**：在旧流程有明确技术失败证据且本轮已启动的门店中，统计自主到达正确菜单和采集验收通过的数量。
- **耗时**：分别记录启动、导航和采集耗时，人工准备时间单列。

汇总分别报告自主到达率、终态准确数及分母、历史技术失败挽回数、救援轮数、导航耗时分布和未执行项；不合并为处理有效率或单一总分。采集完整性另按正确门店、菜品价格可读、菜单无遮挡、截图连续和尾部证据人工核验。未启动、素材版本无法匹配或起始窗口不符合条件的用例单列，不记作 Agent 成功或失败。

### 6.3 离线诊断

19 个固定画面和 R01 历史序列只用于诊断动作语义、坐标命中及终态判断问题，不计入 11 家核心实机评测成绩，不用于证明对新商家的泛化能力。

启动配置、试验报告位置及合成图探测命令见 [批量试验说明](../UFS_Menu_Scraper/macos_runner/ui_tars/README.md)。
