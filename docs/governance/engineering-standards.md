# 工程规范

本文件是 [AGENTS.md](../../AGENTS.md) 的展开版，面向服务端、采集执行、前端与发布链路。规范以“正确性优先、最小变更、按风险验证”为前提，不为了流程增加流程。

## 分层与职责

| 层 | 位置 | 职责 | 约束 |
| --- | --- | --- | --- |
| 传输 | `menu_capture/server.py`、`shared_routes.py` | HTTP 路由、鉴权、参数校验、错误映射 | 不写业务规则，不直接操作执行器内部状态 |
| 业务 | `batch_management.py`、`rejections.py`、`materials.py`、`annotation.py` | 批次、素材版本、审核与标注流程 | 跨模块走显式接口，不共享可变全局状态 |
| 执行 | `uipath_runner.py`、`ui_tars_trial.py`、`windows_desktop.py` | 机器人与桌面执行、协议与超时 | 失败要可归因，不吞异常；平台分支显式判断 |
| 状态与存储 | `store.py`、`shared*.py` | SQLite 事实源、共享分配与同步 | 唯一事实源；迁移只做前向兼容 |
| 展示 | `web-react/` → `web/react/` | React 控制台 | 不在前端复制服务端业务状态；构建产物随代码提交 |

- 新能力优先落在既有层内；跨层需求先加契约，再改实现。
- 拒绝无依据的本地缓存、去重与重试；确需缓存时说明失效条件。

## 技术选型与复用优先

适用于新增或重大重构的通用基础设施（安装/OTA、容器交付、鉴权、网络、调度、存储、可观测性等）、核心依赖选型及跨平台运行机制。简单业务改动和已确认且未变化的技术方案复用既有结论，不强制重复评估。

- **先选型，后设计与实现。** 规划方在 Issue 或关联技术决策记录中明确业务约束、非目标、现有组件、官方标准及候选方案；优先级为平台原生能力、仓库已有合格组件、成熟维护中的框架/SDK、薄适配封装，最后才是必要自研。优先级不是强制引入依赖，须以实际兼容性、风险与总成本决定。
- 至少比较合理的直接复用、薄封装与现有/自研方案；核对官方文档和上游仓库的版本、维护状态、许可证、供应链与安全机制、平台及运行时支持、升级/迁移/回滚、运维与长期维护成本。注明证据来源和日期，不把参考设计等同于已复用，也不把未经验证的能力当作已支持。
- 对高风险或不明确的关键契约先做最小 PoC（真实目标平台、隔离数据/目录/端口），明确通过、失败与未验证项；优先使用小型 fixture 和现有正式产物，不触发完整 CI、不构建产品完整安装包或镜像、不改生产环境。需要扩大验证范围时遵守既有授权及交付规范。
- 明确复用、自研、删除及迁移边界：通用算法、协议和生命周期优先交由合格上游实现，项目仅保留业务规则、必要适配与安全边界；不为复用另造第二套状态机，不机械追求依赖数量或自研代码比例。若成熟方案不能满足关键约束，记录排除证据、最小自研理由、维护责任和验收条件，提交维护者确认后实施。
- 已有自研模块发生重复维护成本或平台兼容故障时，重新比较迁移成本和长期维护收益；不因沉没成本拒绝复用，也不未经验证推倒正在运行的系统。迁移必须保留数据、身份、必要兼容与回退能力，分阶段淘汰旧实现，不长期维护两套等价基础设施。

评审新增基础设施、核心依赖或重大重构时检查上述选型证据和 PoC；缺少必要证据或未获批准即重复自研通用能力，按现有 Review 规则阻断相关设计/实施。普通修复不因此扩大范围，不自动增加 CI 门禁。

## 数据与迁移

- SQLite 数据库、素材与截图属于运行数据，不进入版本库。
- 结构变更必须以前向迁移为主；回滚兼容性必须依据实际旧版本读写契约判断，不能仅凭新增字段具有默认值认定兼容。无法证明兼容时不得自动回滚，并须明确恢复状态与方案。
- 升级前根据候选版本影响保护 `config.local.json`、`secrets.local.json`、SQLite 一致性快照及未同步任务。已有有效快照满足本次恢复要求时应复用，不重复备份。备份应限制访问，不输出密钥。普通软件回滚只切换程序版本，不默认恢复数据库或覆盖升级后新增业务数据。只有实际迁移、删除、覆盖或其他可证实的文件风险才扩大文件备份范围；可重建的交付投影无需重复全量复制。独立数据备份按业务恢复目标管理；涉及文件与数据库共同恢复时保证同一业务一致点。
- 不得修改或清空生产数据；需要变更时先做副本验证。

## 测试与验证

| 改动类型 | 最低验证 |
| --- | --- |
| 纯文档 / 配置 | 按影响检查差异、链接或配置语法。涉及运行配置时验证相关契约。 |
| 服务端路由、共享同步 | `tests/integration/` 下的 `test_server.py`、`test_shared_workbench.py` 等 |
| 采集执行、窗口契约 | `test_windows_compat.py`、`test_environment.py` 与相关回归 |
| 前端 | 按风险运行类型检查、相关 Vitest 或浏览器交互用例。提交涉及产品资源的变更前核对 `web/react`。 |
| 数据库 / 并发 / 权限 | 用隔离数据执行必要的迁移兼容性、竞态、角色与拒绝路径验证。 |
| 安装器 / Hub / 升级回滚 | 开发期使用脚本、契约与隔离集成测试，复用已有安装包和镜像。依赖候选完整产物的用例并入最终集成验收。 |

- 按当前改动确定测试范围，优先复用经过确认且未受影响的证据。需要补证时仅覆盖变化和相关故障路径。
- 同一场景复用现有测试、截图和记录。PR 引用证据即可，避免重复构建、截图、报告或扩大测试范围。
- 区分“代码实现”“测试通过”“真实业务验收”，汇报时分别说明。

## 静态检查与格式

- Python：Ruff，配置在 `app/pyproject.toml`。
  - 门禁规则：`E9`、`F63`、`F7`、`F82`（语法错误、未定义名、无效比较、无效 f-string），当前 0 项。
  - 存量基线：`E4,E7,E9,F` 共 65 项（多语句单行、未使用导入/变量等），按模块逐步治理，不做一次性全量格式化。
  - 本地使用 `uvx ruff check <受影响路径>`。遇到全局配置变动等实际跨模块影响时再扩大检查范围。
- 前端：`tsc -b --noEmit`（`npm run typecheck`）与 Vitest 作为门禁；ESLint 暂不引入，原因见 [治理报告](repository-audit-2026-11.md)，如需引入须先固化基线并只拦截新增问题。
- 编码统一 UTF-8（无 BOM），换行 LF，规则见 `.editorconfig`。

## 前端设计体系

- 入口：[docs/design-system/README.md](../design-system/README.md)。四层模型为 L1/L2 OpenAI Apps SDK UI、L3 自有复合组件、L4 Cloudscape/Carbon 产品模式参考。
- 新页面先复用 `src/components` 契约；表格、筛选、分页、批量操作、设置布局、表单、弹窗/抽屉、图片预览与反馈不得在页面内重复实现。
- 视觉只使用官方语义 Token；不引入 Ant Design/Carbon/Cloudscape 运行时依赖或额外主题。
- Storybook 为开发依赖：`npm run storybook`、`npm run build-storybook`；产物 `storybook-static/` 已忽略，不进入安装包或镜像。
- 组件状态至少覆盖适用的正常、加载、空态、错误、禁用、长文本与窄容器；交互测试优先稳定 DOM/布局断言。

## 协作与交付决策

维护者决定产品优先级、业务规则与授权范围；规划/Review Agent 负责调研、方案取舍、Issue、独立审查与发布建议；Coding Agent 负责读取最新规范、实现、测试、提交 PR 和获授权的发布运维。常规实现细节自主决定；跨范围、业务语义、兼容性或安全边界变更先回到规划方。规划方不得将未验证的推测作为阻断缺陷；执行方不得以自己的汇报代替独立 Review。维护者可一次授权一轮交付的合并、CI、发布、部署及有界重试，记录范围；未授权事项仍需确认。

默认流程：需求 → Issue（目标、范围、非目标、验收）→ 从 main 创建短生命周期分支 → 最小实现与相关测试 → PR → 独立 Review → 授权合并 → 按需集中发布 → OTA 与实际验收。纯文档或简单修复可直接以 PR 承载需求，不强制额外 Issue。PR 关联 Issue；若尚需生产验收，用 Refs #编号，避免合并自动关闭；全部验收满足后关闭。分支建议 feat/编号-简述、fix/编号-简述 或 docs/简述；保持 main 可交付，不新增长期 develop 分支。互不相关重构分离，不要求固定行数或重复报告。

Review 结论为通过、条件通过、需修复或证据不足。P0 为严重数据/安全/核心服务风险；P1 为违反本轮验收或明确的实质缺陷；两者仅在证据支持时阻断。P2 为非阻断优化，Note 为建议。阻断项说明代码位置/证据、影响、最小修改和验证；未验证风险标记待核实。不得为追求完美强制无关重构；条件通过须明确条件并核实后才可合并。审查绑定 PR head SHA，新提交仅补审受影响范围。

执行汇报统一为：Issue/PR 与提交 SHA、实际改动、验证命令及结果、未验证事项/阻塞、下一步。引用现有日志和报告，不重复制作。产品完成、代码合并、CI 通过、正式发布、设备升级分别记录，不互相替代。

## 版本管理

采用 SemVer 2.0.0。产品版本统一为 MAJOR.MINOR.PATCH，Git Tag/Release 使用 v 前缀，应用和清单使用无前缀版本；资产命名沿用 [更新契约](../updates/README.md) 和实际构建脚本，不为统一外观重命名现有资产。Hub 与 Worker 共用发布版本，实际设备版本独立报告；通信协议、数据 schema 与更新清单是兼容性契约，不以版本号相等代替兼容测试。

0.x 阶段采用本项目约定：兼容修复和小型内部优化增加 PATCH；兼容新能力或重大改进增加 MINOR；不兼容变更至少增加 MINOR 并显式记录迁移与混合版本限制。1.0.0 由维护者在稳定契约明确后决定；此后不兼容公开契约增加 MAJOR，兼容新增功能增加 MINOR，兼容修复增加 PATCH。多项修改取最高适用级别；纯开发文档/测试不单独发布。预发布按需要使用 -rc.1 等 SemVer 后缀并标记 prerelease，不强制每次生成 RC。正式版本不得使用 build metadata 区分不同产物，构建身份由 commit SHA 和摘要记录。

发布前核对实际远端正式版本及 Tag，选定未占用、可正确排序的版本；已发布 Tag、资产及清单不得覆盖，失败候选未发布时可复用版本号但必须重新绑定真实候选提交与验收证据。CHANGELOG.md 的 Unreleased 记录值得用户了解的变化，发布时按实际范围归入版本及日期，不复制 Git 日志，不虚构已发布条目。正式发布记录包含版本、commit、CI run、资产摘要、兼容性限制和回滚方式。

## 发布与备份的风险分级

普通业务代码/Prompt/UI：相关本地检查、正式发布必要门禁、现有 OTA 健康检查即可；不默认增加全历史文件备份、全业务人工回归或灾难恢复演练。数据库/并发/共享契约/安全/安装器/OTA：增加对应隔离验证，确认混合版本兼容、回滚及数据风险；未知影响按较高风险处理。纯文档按差异和链接检查，不打包。

部署优先复用已验收产物。按真实兼容关系和空闲状态确定 Hub/Worker 更新顺序，先验证一个适当设备/服务，再推广；不新建远程部署编排系统。离线设备记录待升级，不宣称完成；不得中断活跃采集。检查真实版本、健康及受影响业务；失败停止推广，使用既有安全回滚，若数据不兼容则停止自动回滚并提交恢复方案。

备份与发布是两个职责：已有程序版本/镜像支持软件回滚；仅在存在不可逆数据风险时使用最小数据库恢复点。生产数据恢复、覆盖或清理属于独立授权事项。

强制备份策略：

1. 日常软件升级默认不创建业务数据备份。
2. 禁止全量复制 Hub Docker 数据卷。
3. 禁止全量复制 Worker 生产数据目录。
4. 禁止备份原始素材、二维码候选、截图及交付目录。
5. 禁止为升级备份完整源码、运行环境与安装目录。
6. 仅当存在不可逆数据库迁移或明确的数据修改风险时，才允许创建最小必要的 SQLite 一致性恢复点（`sqlite3.backup`）。
7. 超出上述范围的备份必须获得维护者明确授权。
8. 不得以安全、谨慎、验收或回滚为理由擅自扩大备份范围。
9. 清理误建备份前，确认复制进程已停止，并核验目标确为本次新增的冗余副本，禁止误删原始数据。
10. 普通版本升级直接复用现有 Velopack、Docker Compose、持久化数据卷及兼容回滚机制。

## 发布与云端构建

所有当前及后续开发任务采用本地按风险验证，完整 CI 集中在交付末期。

- 正式 Release 必须附 `update-manifest.json`（契约见 [docs/updates/README.md](../updates/README.md)）；缺清单或校验失败的版本不得作为可更新版本提供。
- 更新发现只允许固定仓库正式 Release；禁止接受前端传入的任意 URL、版本路径、镜像或命令。
- 下载/安装/镜像切换必须有独立执行器、事务锁与健康检查；不得把 Docker Socket、宿主机 shell 或任意路径暴露给业务容器/浏览器。
- CI 临时 artifact 默认保留 14 天；正式 Release 资产独立永久保留。

1. **开发与评审**期间，Issue 实施、提交、PR、合并及标签推送均不得主动触发 GitHub Actions。禁止在此期间构建完整 Windows 安装包、Hub 镜像或发布归档。合并依据本地验证证据及仓库现行保护规则。
2. **集成交付**在本轮所有开发任务完成后集中进行。锁定候选提交、版本和必要的升级基线，默认同一交付手动运行一次 [发布工作流](../../.github/workflows/windows-release.yml)。各 Issue 共用这次完整验收。工作流覆盖前端、Python 静态检查、Windows 安装与恢复、Hub 数据卷与升级回滚。
3. **集成失败**时先读取该次日志，针对失败原因在本地隔离修复和验证。重新派发、重跑失败作业或重跑整条工作流前，均须在维护者明确授权范围内（可在本轮开始时一次授权有界重试）；超出范围另行确认。更换提交、分支或版本号不重置本轮次数。
4. **交付产物**使用已验收的同一份 EXE、Hub 镜像归档、更新清单和校验值，按提交、版本与摘要核对。显式选择 `create_release` 时，工作流可用验收产物准备 Release 草稿。正式发布和生产部署须在用户明确授权范围内（可一次授权本轮两者），已正式发布的版本禁止覆盖。

## 文档规范

- 当前有效文档位于 `docs/`；历史阶段文档归档到 `docs/archive/<年月>-<主题>/`，索引在 `docs/archive/README.md`。
- 产品需求放 `docs/product/`；发布变更记录在 `CHANGELOG.md`。
- 文档中的命令与路径使用相对路径或环境变量，不写个人机器绝对路径。

## 评审清单

- 涉及基础设施、核心依赖或重大重构时，是否完成必要的复用评估、关键 PoC 和自研边界说明。
- 是否在正确的层修复，是否存在跨层直连或状态重复。
- 是否覆盖失败路径与回滚路径，错误是否可诊断。
- 是否新增未忽略的运行产物、密钥或大文件。
- 验证证据是否与改动风险匹配，是否说明了未完成事项。
