# 工作区与运行时存储治理

状态：生效（#105）。本文是唯一细则，`AGENTS.md` 只保留强制摘要，不重复完整规则。

## 1. 适用范围

Windows 开发主机（DESKTOP-3UPCJQU）上的源码、Worktree、运行时数据、构建产物、备份与归档。

不覆盖：业务项目模型（#102）、OTA 协议与安装器（#101）、产品功能本身。

## 2. 目录契约

| 路径 | 用途 | 约束 |
| --- | --- | --- |
| `D:\menu-agent` | 唯一 Git 主仓 | 只放源码、Git 数据、开发配置；禁止长期写入运行数据 |
| `D:\ma-workspace\development\worktrees` | 进行中 Issue 工作区 | 命名 `issue-<编号>-<简名>` |
| `D:\ma-workspace\production\worker` | Worker 业务数据 | 由 `MENU_CAPTURE_HOME` 指向；迁移在维护窗口执行 |
| `D:\ma-workspace\production\hub` | Hub 部署配置与管理清单 | 真实数据在 Docker 卷，不落此目录 |
| `D:\ma-workspace\testing` | 公共测试素材与独立测试环境 | 每 Issue 独立数据根、端口、身份 |
| `D:\ma-workspace\release` | 安装包与校验清单 | 只保留当前版本与必要回滚版本 |
| `D:\ma-workspace\cache` | 可重建缓存 | 可随时清空 |
| `D:\ma-workspace\backups` | 数据库一致性与迁移恢复点 | 必须附清单 |
| `D:\ma-workspace\archive` | 有明确理由的历史文件 | 必须记录保留原因与恢复方式 |
| `D:\MenuCapture` | 正式交付目录（Hub bind mount） | 保持原地，不改路径 |
| Docker 数据卷、Velopack 安装根 | 官方布局 | 不迁移，不手工清理底层目录 |

主仓保持 `D:\menu-agent` 原地不动：生产安装根、计划任务、`MENU_CAPTURE_HOME` 与 Worktree 注册均引用该绝对路径，重命名收益低、连锁风险高。

## 3. 处理规则

### 3.1 源码与 Worktree

- 一主机一主仓；主仓原地不动，只做减法（把运行数据移出）。
- 新 Worktree 只能建在 `D:\ma-workspace\development\worktrees`；禁止在盘根新建 clone。
- 创建前执行 `git fetch` 并检查 `git worktree list`，避免与已有工作区冲突。
- 回收前确认：无脏文件、无未跟踪文件、无独有提交、无独有截图或业务数据。
- 独有提交先推送；推送不可用时用 `git bundle` 到有凭据的机器推送。未提交修改先导出 patch。
- 只用 `git worktree remove`；禁止 `--force`、`reset --hard`、`clean -fdx` 绕过保护。

### 3.2 生产运行

- 生产只从 Velopack / Inno 安装根运行，不依赖主仓工作区或临时 Worktree。
- 业务数据、设备身份、配置、离线队列、截图、结果、更新事务与恢复包存放在稳定数据根。
- 程序升级、回滚、重装不得丢失上述数据。
- 不停止活跃采集，不改生产服务、启动项、配对、网络或数据路径，除非有维护窗口与回滚方案。
- 不直接清理 Docker 底层目录；卷、镜像、构建缓存由 Docker 管理。

### 3.3 依赖与构建

- 依赖由锁文件与官方包管理器管理；共享下载缓存，不备份 `.venv`、`node_modules`、编译缓存。
- 禁止删除生产 release 自带的 `node_modules` 与运行时。
- 构建输入绑定 commit / 锁文件；临时输出与发布产物分离，避免并发覆盖。
- 正式产物以 GitHub Releases、OCI 仓库为事实来源；本地只保留当前与必要回滚版本。

### 3.4 备份与归档

- 取消默认整仓复制；已推送源码由 GitHub 管理，独有源码单独保护。
- SQLite 使用一致性备份（含 WAL）；禁止把复制活跃主库当作完整备份。
- 每份备份附清单：来源、时间、版本/commit、文件清单、必要校验、保留原因、恢复方式、到期日期。
- 同盘备份不防磁盘故障；重要数据需独立设备或远端副本。
- 归档只保存有明确价值的历史文件；不把未知文件无限期搬入归档。

## 4. 保留策略

| 类型 | 保留周期 |
| --- | --- |
| 日常数据库备份 | 最近 7 天 |
| 每周备份 | 最近 4 周 |
| 每月关键备份 | 最近 3 个月 |
| 迁移前恢复点 | 验收通过后 30 天 |
| 正式安装包 | 当前版本及必要回滚版本 |
| 本地临时构建产物 | 任务完成后 7 天 |
| 测试环境 | Issue 结束后回收 |
| 独有业务数据 | 不自动删除 |
| 活跃事务恢复包 | 事务安全结束前不得删除 |

达到保留期只是允许复核，不等于自动删除；仍有业务或恢复价值的内容继续保留并记录原因。

## 5. 清理流程

1. dry-run 盘点：`python ops/storage_inventory.py`，输出候选、归属、实际占用、预计回收空间与拒绝原因。
2. 执行前重新校验：路径在受管范围内、无进程占用、Git 状态未变、保留条件未过期。
3. 仅清理可重建、无使用者、无生产引用且满足保留期的内容。
4. 生产数据、唯一文件、未知目录、大型历史备份必须单独审批并提供证据。
5. 记录实际回收空间，同盘移动量单独统计。

## 6. 禁止事项

- 新增存储管理平台、管理 UI、常驻服务、业务数据库或自研备份框架。
- 重复实现 Git、Docker、Velopack 等成熟工具已具备的能力。
- 全盘自动扫描删除、危险递归强删、`docker system prune -a`、`docker volume prune`。
- 为目录整齐而强制改变官方框架的目录结构。
- 未经授权删除唯一业务数据或影响生产服务。
