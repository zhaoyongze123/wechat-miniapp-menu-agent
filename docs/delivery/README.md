# 合格成品目录

Hub 把当前有效的合格门店截图实时同步到宿主机可见的交付目录，供人工复制到 U 盘或移动硬盘。Issue #73。

## 结论先行

- **一个共享端、一份合格目录、一店一个文件夹、一店只保留最新有效轮次的完整菜单截图。**
- 交付目录是**派生视图**，唯一业务事实源仍是 Hub 的任务与审核状态；同步服务不新增第二套合格状态机。
- 采集端（A/B/更多台）只负责采集与上传，不各自维护成品目录；采集端既有的离线缓存、采集输出与补传机制不变。
- 内部历史记录按现有业务规则保留，但绝不混入交付目录。

## 目录结构

```
<挂载根>/
├── 合格/                      # 唯一成品交付目录（宿主机可见）
│   ├── E02412-门店名/
│   │   ├── page-0001.png
│   │   └── page-0002.png
│   └── E02413-另一家门店/
└── .menu-capture-staging/    # 构建中目录，切换完成即清理
└── .menu-capture-trash/      # 被替换的旧目录，随后删除
```

- 只收录直接位于结果目录下、命名符合 `^page-\d+\.png$` 的截图，按页码排序。
- 目录名为门店名清洗后的结果（Windows 非法字符、保留名、首尾点、超长截断）；同名不同门店用门店编号或短哈希后缀区分。
- 暂存与回收目录放在挂载根下，不进入交付目录，也不放在只读容器根文件系统。

## 收录口径

### 当前有效结果

以 Hub 的 `materials.effective_capture_tasks()` 为准（每个未删除批次的最新发布快照），且 `capture_results.store_state(task) == "captured"` 视为合格（待检查也计入合格）。

### 历史存量（首次初始化）

首次部署后自动初始化全部历史存量，无需重新采集或人工整理：

| 来源 | 容器内路径 | 识别方式 |
| --- | --- | --- |
| 共享采集结果 | `data/` 下任务 `output_dir` | 当前有效任务直接引用 |
| 旧版输出目录 | `output/` | 向下最多 3 层，找直接包含 `page-*.png` 的目录 |
| 历史来源素材 | `legacy-sources/` | 同上，并校验 PNG 文件头 |

- Issue #73 核查基线为 616 + 700 + 18 = 1,334 家；**基线不写死**，实际数量以每次扫描结果为准。
- 与当前有效任务输出重合的目录不重复计入。
- 业务状态不是合格、只含无效 PNG、已有当前有效轮次的同名目录会被排除并计数。
- 同一门店名存在多轮历史目录且没有任务版本可裁决时，判定为歧义并报告，**不猜测**当前轮次。
- 初始化按时间片分批执行（默认每轮约 8 秒），逐店写入索引；中断后从索引续传，重复执行幂等。
- 初始化期间正常采集与审核不受影响；审核结果变化会在后续轮次自动反映。

### 初始化核对

完成后输出门店数、图片数、总字节数与内容摘要（逐文件 SHA-256 汇总），在「合格清单」的「初始化核对与排除项」中可查看，并持久化到 `data/delivery-index.json`。

## 最新整轮覆盖

同一门店有多轮采集时，以 Hub 认可的当前有效采集结果为准：

- 身份优先用 `store_id`（`store:<id>`）；无 `store_id` 时用门店名（`name:<门店名>`）。
- 同一身份跨批次/多轮，按业务版本 `(batch_version, material_version, updated_at)` 选最新，**不看图片文件修改时间**。
- 选中的轮次整目录构建后原子替换；旧目录整体移出，新轮次中不存在的截图不会残留。

明确禁止：多轮截图合并、仅覆盖同名文件、新图追加到旧目录、用历史图片补足当前缺失、按文件修改时间猜最新、旧轮次迟到上传覆盖新轮次。

### 业务状态变化

| 业务变化 | 交付目录行为 |
| --- | --- |
| 采集成功 / 待检查（合格口径） | 新增或整轮替换 |
| 审核通过 | 保持 |
| 标记不合格 | 移出 |
| 打回素材清洗 | 移出 |
| 重采后当前轮次失效 | 移出 |
| 重采成功 | 整轮替换 |
| 撤销不合格 | 恢复 |
| 历史批次迟到结果 | 不影响当前有效轮次 |
| 批次删除 / 恢复 | 删除后移出，恢复后重新同步 |
| 重启 | 读取索引恢复，抽检缺失文件 |
| 人工误删交付文件 | 自动重建，不回写业务状态 |
| 业务合格但截图缺失 | 移出交付目录，不拿旧图冒充当前成品 |

## 部署配置

交付目录必须通过 **Bind Mount** 提供；命名卷在宿主机上不可见，不能作为交付目录。

| 变量 | 作用 | 默认 |
| --- | --- | --- |
| `MENU_CAPTURE_DELIVERY_MOUNT` | 宿主机挂载根，例如 `D:/MenuCapture` | `./delivery`（compose 同级） |
| `MENU_CAPTURE_DELIVERY_ROOT` | 容器内交付目录，固定为挂载根下「合格」 | `/var/lib/menu-delivery/合格` |
| `MENU_CAPTURE_DELIVERY_HOST_PATH` | 界面展示与复制的宿主机路径 | `${MENU_CAPTURE_DELIVERY_MOUNT}/合格` |
| `MENU_CAPTURE_DELIVERY_POLL_SECONDS` | 同步轮询间隔 | `5` |

- 未配置（无 `MENU_CAPTURE_DELIVERY_ROOT` / `HOST_PATH`）时服务降级为「未配置」，不写入任何目录。
- 挂载根不存在或不可写时状态为「不可用」并暂停写入，不会清空既有交付目录。
- 容器以 UID 10001 运行；Linux 宿主机需保证挂载目录对该用户可写（Windows Docker Desktop 一般无需额外处理）。
- 容器受 `read_only: true` 约束，因此暂存/回收目录必须位于 Bind Mount 内。

### 打开目录

- Hub 与交付目录同机且平台为 Windows/macOS 时，前端「打开合格目录」调用 `POST /api/delivery/reveal` 真实打开文件管理器。
- 容器内运行时无法打开宿主机资源管理器，按钮禁用并说明原因，改用复制路径；不提供假按钮。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/delivery/status` | 状态、统计、初始化核对、内容摘要、打开能力 |
| GET | `/api/delivery/stores?page&size&q&batch_id` | 合格门店分页列表与批次选项 |
| POST | `/api/delivery/sync` | 触发一次重新核对 |
| POST | `/api/delivery/reveal` | 打开宿主交付目录；不支持时返回 409 |

仅 Hub 装配该服务；Worker/standalone 访问返回 404。

## 前端

质量审核页新增「合格清单」视图（`/quality?view=qualified`）：

- 统计卡：合格门店、已同步、菜单截图、成品大小。
- 目录卡片：宿主机路径、复制路径、打开目录、重新同步、最近同步时间、内容摘要与初始化核对。
- 门店表格：门店、批次、截图数、大小、同步状态；点击查看详情与在线预览（历史存量未关联任务时提示按路径查看）。

## 已知边界

- 历史存量目录的真实布局需在生产只读核查；`legacy-sources/` 早期 18 家的截图性质仍待确认，当前按 PNG 文件头与命名规则纳入，无法确认时报告歧义而不猜测。
- 同名不同门店若旧目录名与任务门店名格式不一致，可能无法按名称排除；以实际扫描报告为准。
- 生产冻结期间未做真实浏览器 + 生产数据验收，证据边界以 Issue 与验收记录为准。
