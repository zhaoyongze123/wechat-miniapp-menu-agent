# GUI Agent 菜单自动采集系统：长期开发与优化指导思想

## 一、核心目标

本项目的目标是通过 GUI Agent 自主操作不同商家的点餐系统，尽可能进入可浏览的菜品菜单，并交由现有自动化程序完成截图采集。

**我们追求的是在真实、复杂、未知的场景中，持续提高任务的有效处理率，而不是实现一套覆盖所有页面、所有操作步骤的固定自动化脚本。**

GUI Agent 的操作具有动态性和不确定性。即使面对同一家门店，不同执行过程中也可能出现不同的页面状态、操作路径、模型调用次数和最终判断。

不要求每次执行完全一致，也不要求操作次数绝对最少。

优化应以真实任务效果为依据，在有效性、稳定性、效率和系统复杂度之间取得平衡。

## 二、核心架构原则

### 1. Agent 是唯一的业务决策主体

Agent 负责理解当前页面、规划下一步操作、执行导航、处理阻碍，并自主判断是否达到任务目标。

外部程序负责提供截图、点击、滚动、窗口操作等工具，以及任务管理、技术错误处理、日志记录和最终截图采集。

**不在 Agent 外部构建第二套页面状态机、关键词判断系统或业务决策逻辑。**

尤其不能出现 Agent 已经作出判断，Python 又根据 OCR、页面关键词或预设规则重新决定业务终态的情况。

### 2. 以任务目标驱动操作，而不是以页面类型驱动操作

Agent 的核心目标是找到可采集的菜单，而不是按照预设顺序完成某些页面操作。

不同商家的点餐系统可能通过小程序、微信网页、浏览器或其他界面提供服务。

进入后可能是首页、订单、会员、购物车、广告或其他页面。它们可能只是中间状态，也可能提供通往菜单的入口。

因此：

- 不根据页面名称直接排除某条路径。
- 不预设固定的点击顺序或导航路线。
- 不因为页面与已有案例不同就认定失败。
- 不要求所有商家使用相同的页面结构。

Agent 应结合当前可见信息，自主决定是否继续、返回、切换窗口、关闭遮挡或尝试其他入口。

**页面是观察对象，不是预先定义好的状态集合。**

### 3. 保持必要的安全边界

自主执行不意味着可以执行所有操作。

本项目只需要浏览菜单和获取菜单截图，不需要参与真实交易。

不得提交订单、支付、充值、领取优惠、修改现有顾客订单或购物车，也不应擅自更改门店、桌位等实际业务状态。

对于登录、授权、定位等前置步骤，应在允许的操作边界内寻找可行路径，不能通过不必要的授权或业务操作强行完成任务。

### 4. 保持执行链路简单、职责清晰

系统应尽量维持一套统一的执行架构：

- **任务管理层**：管理任务、批次、状态、执行记录和结果。
- **Agent 层**：自主理解页面、规划并执行导航，决定业务终态。
- **工具执行层**：通过 UiPath 等工具完成真实 GUI 操作。
- **截图采集层**：接收 Agent 交接的菜单区域，执行滚动截图和保存。

不同层次之间通过明确的工具协议和结果契约协作。

不因为个别失败案例引入新的 Agent、并行导航引擎、重复业务判断模块或复杂状态机。

技术选型可以变化，但这些职责边界应保持稳定。

## 三、Prompt 与 Skill 的设计原则

### 1. 优先描述目标、约束和判断原则

Prompt 应清楚告诉 Agent：

- 最终任务是什么。
- 当前提供了哪些信息和操作能力。
- 哪些操作允许，哪些不允许。
- 什么情况下可以成功交接。
- 什么情况下应判定无法采集或需要人工检查。

尽量避免把 Prompt 写成逐步操作教程。

### 2. Skill 提供可复用经验，而不是固定规则

Skill 用于帮助 Agent 理解常见问题和处理思路，例如订单页返回菜单、会员入口、弹窗、人数选择、加载异常和窗口切换。

这些内容应作为参考经验，而不是必须逐项执行的规则。

如果经验与当前截图冲突，应优先根据实际界面判断。

当前业务经验较少且集中时，可以直接加载同一份 Skill，不必为了形式上的模块化引入额外的检索和调用步骤。

只有当内容规模和使用场景确实需要时，再考虑拆分。

### 3. 避免规则之间相互冲突

新增经验前，应检查是否与已有原则矛盾。

例如：

- 会员中心可能是无关入口，也可能通往菜单。
- 订单页不是采集目标，但可能通过底部导航进入菜单。
- 广告可能不影响浏览，也可能完全遮挡菜品。
- 无法下单不代表无法查看菜单。

对于这类情况，应提炼共同的判断原则，而不是不断增加例外条件。

## 四、成功交接和结果判断

### 1. success：已达到可采集状态

Agent 应确认当前已经进入真实菜品菜单，并且页面适合直接开始截图。

不能因为菜单在弹窗背后隐约可见，就认定可以采集。

如果存在遮挡菜品的弹窗或浮层，应先尝试处理，并根据处理后的最新页面重新判断。

成功后输出可用的菜单区域，交由截图程序继续执行。

### 2. unqualified：有明确证据表明无法采集

必须有可见、充分的依据，例如点餐服务明确关闭、二维码失效且无法进入菜单，或明确要求到店才能查看菜单。

不能把暂时加载失败、操作未成功或网络异常直接等同于业务不合格。

### 3. needs_review：合理尝试后仍无法确定

当页面持续异常、操作无法完成、缺乏足够证据或遇到当前工具无法处理的情况时，可以返回待人工检查。

**不确定时保留不确定性，不为了提高表面成功率而强行给出结论。**

### 4. 区分业务终态与技术结果

Agent 的业务判断、工具执行情况和截图采集结果应独立记录。

例如：

- Agent 判断成功，但截图工具超时。
- Agent 判断无法采集，但运行程序正常。
- 模型输出格式错误，导致没有形成有效业务终态。

这些情况不应混为同一种失败，也不应让技术错误覆盖 Agent 原始判断。

## 五、工具能力与执行效率

### 1. 工具应保持通用

优先提供点击、滚动、等待、窗口发现、窗口切换等通用操作能力。

当真实问题证明现有工具不足时，可以补充必要的新动作。

不针对某个商家编写专属点击流程，也不为每种页面设计专门的工具。

如果二维码打开的是不同类型的窗口，应优先考虑通用的窗口发现、操作和安全关闭能力，而不是开发第二套页面导航程序。

### 2. 不追求最短路径

Agent 可能需要探索、等待、返回或尝试不同入口，这些操作本身不一定是无效操作。

不能仅因为某家门店模型调用次数较多，就认定存在需要修复的问题。

应结合原始截图、动作记录和页面变化，判断是否存在具有共性的低效行为。

优化重点包括：

- 明显无进展的重复操作。
- 不必要的等待与窗口切换。
- 输出协议错误导致的额外调用。
- 对任务目标理解不准确造成的绕路。
- 工具执行失败但未获得有效反馈。

**优先减少没有价值的操作，而不是限制所有操作。**

### 3. 截图阶段保持简单

Agent 在交接前负责确保菜单处于可采集状态。

交接后由现有截图程序执行滚动与保存，不要求模型持续参与每一页截图。

只有真实测试证明存在普遍性的截图技术故障时，才考虑针对截图执行层进行必要改进。

不提前设计复杂的实时页面理解与自动恢复系统。

## 六、发现问题后的优化方法

### 1. 从真实执行记录出发

每次出现失败、低效或异常，优先查看：

- Agent 实际看到了什么。
- 当时作出了什么判断。
- 选择了什么操作。
- 工具是否真正执行。
- 执行后页面有什么变化。
- 最终结果为什么不符合预期。

不能仅凭最后的失败结果推测原因。

### 2. 优先提炼共性问题

一个门店失败，不意味着需要立刻新增一条规则。

应判断它是否揭示了更普遍的问题。

例如两个商家都出现中心弹窗遮挡菜单，真正需要优化的是“可采集状态”的判断标准，而不是分别识别两个商家的广告。

**优化应解决一类问题，而不是只解决一个案例。**

### 3. 优先选择最小有效改动

建议按以下顺序考虑解决方案：

1. 是否可以通过更清楚的任务目标和判断原则解决？
2. 是否可以通过调整已有 Skill 中的通用经验解决？
3. 是否是工具反馈、动作协议或执行能力存在问题？
4. 是否确实需要修改执行层代码或增加通用工具？

不是所有问题都适合通过 Prompt 解决，也不是所有问题都值得增加代码。

应根据真实根因选择最简单、最有效的修改方式。

### 4. 每次改动都要验证收益与副作用

修改后，应优先针对问题案例进行测试，再回归已有成功案例。

不能只确认原来的失败案例变成功，还要观察是否导致其他门店退化。

如果一项修改只改善个别情况，却显著增加整体调用成本、误判或系统复杂度，应重新评估其价值。

## 七、长期评估指标

以**有效处理率**作为主要指标，同时结合以下维度评估：

| 指标 | 关注重点 |
| --- | --- |
| 有效菜单采集率 | 实际获得可用菜单截图的比例 |
| 有效处理率 | 有效采集及正确判定无法采集的比例 |
| 终态准确性 | 成功、不合格、待检查是否有充分依据 |
| 执行稳定性 | 技术故障、协议错误和异常中断情况 |
| 执行效率 | 模型调用次数、无效动作、总耗时和成本 |
| 泛化能力 | 面对新商家、不同页面结构时的处理表现 |
| 系统复杂度 | 为获得效果提升所增加的维护成本 |

测试必须区分不同版本、执行条件和样本范围。

小样本成功率只能作为阶段性参考，不能当作系统在所有场景中的固定表现。

## 八、长期坚持的开发原则

1. **目标驱动，而非步骤驱动。**
2. **Agent 自主决策，外部程序只提供工具与执行保障。**
3. **从实际截图和执行证据出发，不依赖预设页面状态。**
4. **Skill 提供经验，不约束为固定导航流程。**
5. **优先修复共性问题，不为个别案例堆积特殊规则。**
6. **优先复用现有能力，不轻易增加系统层次。**
7. **以有效处理率为核心，不以最少调用次数为唯一目标。**
8. **保留合理的不确定性，不追求表面上的百分之百成功。**
9. **每次改动都通过真实回归验证，避免解决旧问题又引入新问题。**
10. **技术框架可以更换，但业务决策权和系统职责边界不随意改变。**

## 九、最终指导思想

**本项目不是通过不断枚举页面情况，让 Agent 按照我们预先设计的流程完成任务；而是通过明确目标、提供必要工具、积累通用经验和持续分析真实执行结果，逐步提高 Agent 在未知环境中的自主任务完成能力。**

我们接受 Agent 具有一定的不确定性，不追求每次执行路径、调用次数和最终判断完全一致，也不试图覆盖所有可能出现的页面和异常。

未来无论更换模型、开发框架、编程语言还是自动化工具，都应优先保持架构简单、决策权清晰、工具通用，并通过真实场景的持续迭代，提高系统的有效处理率、稳定性和泛化能力。
